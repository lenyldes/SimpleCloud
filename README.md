## Что это такое?

Лёгковесное и безопасное self-hosted‑хранилище файлов для домашнего сервера. Проект построен на микросервисной архитектуре и полностью покрыт CI/CD‑циклом.

> P.S. \
> Сейчас проект на этапе тестирования и отладки — возможны сбои или отклонения в работе отдельных компонентов и сервисов.

## Зачем нужен этот проект

У меня есть домашний сервер, и в какой‑то момент захотелось перестать платить за коммерческие облачные диски и развернуть своё решение.

Сначала я присмотрелся к популярным Open‑Source‑вариантам — в первую очередь к Nextcloud. Но на практике он оказался слишком громоздким: PHP, Apache, Redis, тяжёлая база данных и десятки предустановленных плагинов, которые мне не нужны. На обычном домашнем железе Nextcloud потреблял заметно больше ресурсов, чем требовалось для простой задачи — надёжно загружать, хранить и скачивать файлы.

Так появился SimpleCloud — минималистичное, быстрое и безопасное хранилище без лишнего оверхеда, рассчитанное на ежедневное личное использование. Кроме того, проект стал отличной площадкой, чтобы отработать DevOps‑практики на реальной задаче: от контейнеризации и сетевой безопасности до сквозного CI/CD с автоматическим деплоем.

### Сравнение: Nextcloud vs SimpleCloud

| Критерий | Nextcloud | SimpleCloud |
| :--- | :--- | :--- |
| **Потребление RAM на старте** | ~500 МБ – 1,5 ГБ | **~30–50 МБ** |
| **Время холодного старта** | 30–60 секунд | **< 2 секунд** |
| **Стек сервиса** | PHP + Apache + Redis + MySQL | **Чистый скомпилированный Go + PostgreSQL** |
| **Сложность инфраструктуры** | Десятки фоновых модулей, сложная миграция | **Два компактных Docker‑контейнера** |
| **Назначение** | Корпоративный портал «всё в одном» | **Фокус на скорости, безопасности и хранении файлов** |

## Стек технологий

- **Бэкенд:** Go (REST API, сессионная аутентификация, строгая изоляция пользователей, квотирование).
- **База данных:** PostgreSQL 16 (метаданные файлов, иерархия папок, хеши SHA‑256, учётные записи пользователей).
- **Фронтенд:** Vanilla HTML/CSS/JS (лёгкий интерфейс без тяжёлых фреймворков и сборщиков, drag‑and‑drop, предпросмотр медиа).
- **Инфраструктура и сеть:** Docker, Docker Compose, Nginx (Reverse Proxy, Rate Limiting, Security Headers), Caddy (TLS).
- **CI/CD и автоматизация:** GitHub Actions (автоматический линтинг `golangci-lint`, интеграционные тесты с Postgres Service Container, контроль покрытия >85 %, SSH‑деплой).

## Быстрый запуск

### Требования

- Docker Engine 20.10+
- Docker Compose v2+

### Установка и старт

1. **Клонируйте репозиторий:**
   ```bash
   git clone https://github.com/lenyldes/SimpleCloud.git
   cd SimpleCloud
   ```

2. **Настройте переменные окружения:**
   ```bash
   cp .env.example .env
   # При необходимости измените пароли и квоты в .env
   ```

3. **Запустите контейнеры:**
   ```bash
   docker compose up -d --build
   ```

4. **Вход в систему:**
   - Откройте в браузере: `http://localhost:32214`
   - Логин по умолчанию: `admin@simplecloud.local`
   - Пароль по умолчанию: `change_this_admin_password_on_first_setup` *(обязательно смените после первого входа)*

## Ключевые инженерные решения (DevOps и инфраструктура)

1. **Двухуровневое шардирование файловой системы на уровне ОС:**  
   При хранении миллионов файлов в одной директории файловые системы Linux (например, `ext4`) начинают работать медленнее из‑за поиска по `inode`. В SimpleCloud файлы распределяются по подкаталогам на основе первых 4 символов UUID: `/storage/f4/7a/<uuid>`. Это позволяет сохранять быстрый доступ и масштабируемость на уровне диска.
2. **Эшелонированная сетевая безопасность (Nginx Hardening):**  
   - **Защита от брутфорса паролей:** на эндпоинте авторизации настроен `limit_req` со строгим лимитом 5 r/s и небольшим бурстом.
   - **Защита от DoS на API‑эндпоинтах:** лимит 30 r/s.
   - **Жёсткие заголовки безопасности:** запрет кликджекинга (`X-Frame-Options: DENY`), запрет MIME‑sniffing, политика `Content-Security-Policy`.
3. **CI/CD‑пайплайн полного цикла (GitHub Actions):**  
   - **Fail‑Fast проверка:** автоматический запуск `golangci-lint`.
   - **Интеграционное тестирование:** в раннере поднимается реальный контейнер `postgres:16-alpine` для прогона тестов бизнес‑логики.
   - **Gate качества:** замер покрытия кода с жёстким требованием — не менее 85 %.
   - **Автоматический деплой:** при пуше в ветку `main` пайплайн подключается по SSH к целевому серверу, обновляет репозиторий и перезапускает контейнеры без простоя.

## Практика Spec‑Driven Development и работа с AI‑агентами

Проект разрабатывался по методологии **Spec‑Driven Development** с использованием спецификаций [OpenSpec](https://github.com/Fission-AI/openspec). Моя роль — архитектурное проектирование, формирование формальных требований, код‑ревью и инфраструктурная обвязка.

- **Строгое разделение ролей по TDD:**  
  Разработка велась через специализированных автономных агентов с изолированными правами:
  - `Orchestrator` — анализ требований и архитектурное проектирование фаз;
  - `Test‑Agent` — написание падающих интеграционных и юнит‑тестов (**RED**);
  - `Code‑Agent` — реализация продакшн‑логики до успешного прохождения тестов (**GREEN**);
  - `Audit‑Agent` — независимый аудит безопасности, проверка граничных условий и контроль покрытия не ниже 85 %.
- **Инженерный контроль:**  
  Ни одна строка кода не попадала в репозиторий без ручной верификации, проверки на антипаттерны, успешного прохождения локального тестового стенда и CI/CD‑проверок.

## Тестирование и качество кода

В проекте поддерживается строгое покрытие тестами (Unit + Integration) основных модулей бизнес‑логики:

```bash
# Локальный запуск тестов с подсчётом покрытия
cd services/storage-service
go test -v -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```
*Минимальный порог покрытия для прохождения CI — 85 %.*
