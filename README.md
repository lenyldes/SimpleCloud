## Что это такое?

Легковесное, безопасное self-hosted облачное хранилище файлов для домашнего сервера с микросервисной архитектурой и полным CI/CD циклом.

## Зачем?

У меня есть собственный домашний сервер, и в какой-то момент возникло логичное желание: **перестать платить за коммерческие подписки облачных дисков и развернуть собственное решение.**

Первым делом я обратился к популярным Open Source решениям, в частности к **Nextcloud**. \
Но на практике Nextcloud оказался огромным, перегруженным «комбайном» (PHP, Apache, Redis, тяжелая база данных, десятки предустановленных неиспользуемых плагинов). \
На домашнем железе он потреблял неоправданно много ресурсов ради базовой задачи — надежно загружать, хранить и скачивать файлы.

Так родилась идея **SimpleCloud**: быстрого, минималистичного и безопасного хранилища без оверхеда, созданного для ежедневного личного использования. \
Кроме того, этот проект стал отличной возможностью комплексно отточить DevOps-практики на реальной задаче: от проектирования контейнеризации и сетевой безопасности до построения сквозного CI/CD пайплайна с автоматическим деплоем на сервер.

### Сравнение: Nextcloud vs SimpleCloud

| Критерий | Nextcloud | SimpleCloud |
| :--- | :--- | :--- |
| **Потребление RAM на старте** | ~500 МБ – 1.5 ГБ | **~30 – 50 МБ** |
| **Время холодного старта** | 30–60 секунд | **< 2 секунд** |
| **Стек сервиса** | PHP + Apache + Redis + MySQL | **Чистый скомпилированный Go + PostgreSQL** |
| **Сложность инфраструктуры** | Десятки фоновых модулей, сложная миграция | **Два компактных Docker-контейнера** |
| **Назначение** | Корпоративный портал «всё в одном» | **Фокус на скорости, безопасности и хранении файлов** |

## Стек технологий

- **Бэкенд:** Go (REST API, сессионная аутентификация, строгая изоляция пользователей, квотирование).
- **База данных:** PostgreSQL 16 (хранение метаданных файлов, иерархии папок, хешей SHA-256 и пользователей).
- **Фронтенд:** Vanilla HTML/CSS/JS (ультралегкий интерфейс без тяжелых JS-фреймворков и сборщиков, drag-and-drop, предпросмотр медиа).
- **Инфраструктура и сеть:** Docker, Docker Compose, Nginx (Reverse Proxy, Rate Limiting, Security Headers), Caddy (TLS).
- **CI/CD и автоматизация:** GitHub Actions (автоматический линтинг `golangci-lint`, интеграционные тесты с Postgres Service Container, контроль покрытия >85%, SSH-деплой).

## Быстрый запуск

### Требования
- Docker Engine 20.10+
- Docker Compose v2+

### Установка и старт

1. **Клонируйте репозиторий:**
   ```bash
   git clone https://github.com/lenyldes/SimpleCloud.git
   cd SimpleCloud
   ```

2. **Настройте переменные окружения:**
   ```bash
   cp .env.example .env
   # При необходимости измените пароли и квоты в .env
   ```

3. **Запустите контейнеры:**
   ```bash
   docker compose up -d --build
   ```

4. **Вход в систему:**
   - Откройте в браузере: `http://localhost:32214`
   - Логин по умолчанию: `admin@simplecloud.local`
   - Пароль по умолчанию: `change_this_admin_password_on_first_setup` *(рекомендуется сменить после первого входа)*

## Ключевые инженерные решения (DevOps & Infrastructure)

1. **Двухуровневое шардирование файловой системы на уровне ОС:**  
   При сохранении миллионов файлов в одну директорию файловые системы Linux (`ext4`) начинают деградировать при поиске по `inode`. В SimpleCloud файлы распределяются по подкаталогам на основе первых 4 символов UUID (`/storage/f4/7a/<uuid>`), что гарантирует моментальный доступ и масштабируемость на уровне диска.
2. **Эшелонированная сетевая безопасность (Nginx Hardening):**  
   - Защита от брутфорса паролей через `limit_req` на эндпоинт авторизации (строгий лимит 5 r/s с бурстом).
   - Защита от DoS на API эндпоинты (30 r/s).
   - Жесткие заголовки безопасности: запрет кликджекинга (`X-Frame-Options: DENY`), запрет MIME-sniffing и политика `Content-Security-Policy`.
3. **CI/CD пайплайн полного цикла (GitHub Actions):**  
   - **Fail-Fast проверка:** автоматический запуск `golangci-lint`.
   - **Интеграционное тестирование:** поднятие реального сервисного контейнера `postgres:16-alpine` в ранере для прогона тестов бизнес-логики.
   - **Gate качества:** автоматический замер покрытия кода с жестким требованием **не менее 85%**.
   - **Автоматический деплой:** при пуше в `main` пайплайн подключается по SSH к целевому серверу, обновляет репозиторий и перезапускает контейнеры без простоя.

## Практика Spec-Driven Development и работа с AI-агентами

Проект разрабатывался с применением методологии **Spec-Driven Development** и спецификаций [OpenSpec](https://github.com/Fission-AI/openspec). Моя роль заключалась в архитектурном проектировании, формировании формальных требований, код-ревью и инфраструктурной обвязке:

- **Строгое разделение ролей по TDD:**  
  Разработка велась через специализированных автономных агентов с изолированными правами:
  - `Orchestrator` — анализ требований, архитектурное проектирование фаз;
  - `Test-Agent` — написание падающих интеграционных и юнит-тестов (**RED**);
  - `Code-Agent` — реализация продакшн-логики до успешного прохождения тестов (**GREEN**);
  - `Audit-Agent` — независимый аудит безопасности, проверка граничных условий и контроль покрытия 85%+.
- **Инженерный контроль:**  
  Ни одна строка кода не попадала в репозиторий без ручной верификации, проверки на антипаттерны, успешного прохождения локального тестового стенда и CI/CD проверок.
