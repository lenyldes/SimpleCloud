### 🟡 BUG-4: 2.5. Превью файлов: отсутствие детекции MIME-типов и поддержки Range-запросов (206 Partial Content)
- **Компонент:** Бэкенд (`services/storage-service/internal/handler/file.go:301-307`)
- **Серьёзность:** Medium / Core Feature (Превью файлов и стриминг медиа)
- **Связанный пункт чек-листа:** `2.5. Превью файлов`
- **Проявление:**
  - При скачивании/просмотре любого файла через `GET /api/v1/files/download/{id}` сервер безусловно устанавливает `Content-Type: application/octet-stream`. Из-за этого браузер не может отрендерить текстовые файлы, изображения и медиа в тегах `<img>`, `<video>` или `<audio>`, а скачивает их как бинарники.
  - При отправке заголовка `Range: bytes=0-10` сервер возвращает `200 OK` и всё тело целиком, вместо `206 Partial Content`, `Accept-Ranges: bytes` и `Content-Range`. Это ломает перемотку и стриминг видео/аудио в HTML5-плеере.
- **План исправления:**
  - Реализовать определение MIME-типа по расширению файла (через `mime.TypeByExtension`) или содержимому, с fallback на `application/octet-stream`.
  - Использовать `http.ServeContent` вместо `io.Copy(w, f)` для автоматической и стандартизированной поддержки Range-запросов (206 Partial Content), ETag и If-Modified-Since.

### 🟡 BUG-5: CSRF Origin Mismatch в Nginx Reverse Proxy при обращении через нестандартный порт (32214)
- **Компонент:** Nginx Reverse Proxy (`services/web-frontend/nginx.conf:42, 53`)
- **Серьёзность:** High / Security & Auth (Блокировка отправки форм из браузера)
- **Проявление:**
  - Браузер при запросах на `http://localhost:32214` шлет заголовок `Origin: http://localhost:32214`.
  - В `nginx.conf` настроено `proxy_set_header X-Forwarded-Host $host;`. Переменная `$host` в Nginx не содержит порт хоста.
  - Мидлварь `RequireSameOrigin` в Go сравнивает `u.Host` (`localhost:32214`) с `X-Forwarded-Host` (`localhost`) и возвращает `HTTP 403 Forbidden` (`{"error": "CSRF origin mismatch"}`).
- **План исправления:**
  - В `services/web-frontend/nginx.conf` заменить `$host` в заголовках `Host` и `X-Forwarded-Host` на `$http_host` (который сохраняет оригинальный порт клиента), либо добавить поддержку порта в Go middleware.

### 🟡 BUG-7: Полировка модальных окон (Escape, блокировка при запросе, фокус, XSS-защита и токены тестов)
- **Компонент:** Веб-интерфейс (`services/web-frontend/src`: `app.js`, `modals.js`, `index.html`, `css/modals.css`) и автотесты (`services/storage-service/internal/handler/web_test.go`)
- **Серьёзность:** Medium / UX, Safety & Quality (Поведение модальных окон и защита от рассинхронизации)
- **Связанные пункты чек-листа:** `4.1.b`, `4.2.b`, `6.3`
- **Проявление:**
  1. **Escape не закрывает модалки (`app.js:274-278`):** Глобальный слушатель Escape обрабатывает только дропдаун профиля (`closeProfileDropdown()`). Модалки удаления, создания папок, превью файлов нажатие Escape игнорируют.
  2. **Гонка закрытия при сетевом запросе (`app.js:327-365`):** При клике на "Delete" кнопка подтверждения блокируется, но кнопка "Cancel", крестик "✕" и клик по оверлею остаются активными. Если закрыть окно во время запроса, промис удаления всё равно завершится на сервере, приведя к рассинхрону намерений пользователя и фактического состояния.
  3. **Отсутствие фокуса на безопасной кнопке (`modals.js:197-216`):** При открытии окна подтверждения фокус остаётся на кнопке корзины в таблице, случайное нажатие Space/Enter может сработать непредвиденно.
  4. **Потенциальный риск XSS через innerHTML (`modals.js:209-211`):** Имя файла экранируется через `escapeHtml()`, но архитектурно безопаснее использовать контейнер `<span id="confirm-delete-target-name"></span>` и присваивать имя через `.textContent`.
  5. **Inline-стили предупреждения (`modals.js:209`):** Текст предупреждения о каскадном удалении папки стилизован через инлайн-атрибут `style="..."`. Требуется перенести в класс `.confirm-delete-folder-warning` в `css/modals.css`.
  6. **Доступность (ARIA) (`index.html:257`):** В разметке модалки подтверждения удаления отсутствуют атрибуты `role="dialog"`, `aria-modal="true"` и явные `type="button"` у кнопок.
  7. **Специфика токенов в автотесте (`web_test.go:232-233`):** В `TestWebFrontendDeleteLogicJS` токены `"apiDeleteFile"` и `"apiDeleteFolder"` проверяют наличие объявлений в `api.js`, а не фактические вызовы `window.api.deleteFile` / `deleteFolder` в логике `app.js`.
- **План исправления:**
  1. Реализовать централизованное закрытие активной модалки по клавише Escape в `app.js` (с учётом флага активности сетевых операций).
  2. В `handleConfirmDelete` блокировать крестик, кнопку Cancel и клик по оверлею на время выполнения запроса (свойство `disabled` / флаг `isDeleting`).
  3. При открытии `openConfirmDeleteModal` переводить фокус на кнопку Cancel (`confirmDeleteCancel.focus()`).
  4. В `index.html` и `modals.js` выделить `confirm-delete-target-name` и устанавливать имя через `.textContent`.
  5. Оформить класс `.confirm-delete-folder-warning` в `css/modals.css`.
  6. Добавить атрибуты `role="dialog"`, `aria-modal="true"`, `aria-labelledby="confirm-delete-title"` и `type="button"` в `index.html`.
  7. В `web_test.go` расширить/уточнить проверки вызовов API удаления в `app.js`.
